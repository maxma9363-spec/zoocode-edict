## 1. 流程总览

这项任务按「分拣 → 起草 → 审议 → 派发 → 执行 → 门禁 → 交付 → 终审」的顺序走完，没有跳过任何一步。

| # | 阶段 | 角色 | 在本次运行中做了什么 |
|---|------|------|----------------------|
| 1 | 分拣 | **太子** | 接收请求，并作为正式任务转达。 |
| 2 | 起草方案 | **中书** | 起草执行方案（调研 → 数据模型 → 前端 → 验证 → 文档）。 |
| 3 | 审议 | **门下** | 从可行性、完整性、风险、资源四个维度审议方案；给出准奏或封驳 —— 并在第二轮下达了 3 条硬约束。 |
| 4 | 派发 | **尚书** | 把通过的方案拆解为分阶段任务并派发给六部。 |
| 5 | 执行 | **户部、工部、兵部** | 分别负责调研、构建与部署。 |
| 6 | 质量门禁 | **刑部** | 审查代码与数据，裁定计数口径，并给出 F-2 / F-3 / F-5 建议。 |
| 7 | 交付 | **礼部** | 撰写并对齐面向用户的文档。 |
| 8 | 终审 | **刑部** | 在签署交付前，对代码 + 文档 + 部署做全量回归。 |

这条闭环不是装饰：本次运行中确有两个环节让工作被**退回或拒绝**，而不是被放行交付（见第 4 节）。

## 2. 真实发生的事实要点

**调研阶段（户部）。** 户部产出 [`demo/data/findings.json`](../demo/data/findings.json)，包含 **7 条起因**、**13 条时间线**、**17 位人物与机构**、**19 条来源** —— 每一条都可回溯到所引用的来源。户部**曾一度把人物与机构的计数误报为「5 名个人 + 12 个机构」**，数据集本身无误，错的是**回奏的数字**。

**质量门禁（刑部，阶段3）。** 刑部裁定正确口径为 **12 名个人 + 5 个机构**，将偏差追溯为**户部回奏时的数字颠倒**而非数据缺陷，并给出三项建议：**F-2**、**F-3**、**F-5**。

**修复（工部）。** **F-2 —— 已修复：** 分组标题改为在**运行时动态计算**计数，**零硬编码数字**，页面显示的汇总数字从此不可能与数据脱节。**F-3 —— 已修复：** 某条来源的 `publisher` 字段由 **BSEE** 更正为 **BOEMRE**，与实际发布机构一致。**F-5 —— 前提被证伪，拒绝改动：** 该建议的派发前提是「磁盘上的文件名带有 emoji 前缀」；工部复测后确认**磁盘上并无 emoji 前缀**，因此**拒绝执行该改动并据实上报**，而不是去「修复」一个并不存在的问题 —— 若照单执行，反而会凭空制造出失效引用。

**真实浏览器验证（兵部，阶段5a）。** 兵部以 **Chrome headless** 渲染页面：交付的 `index.html` 为 **3,248 B**，而**渲染后的 DOM 膨胀至 54,530 B** —— 直接证明 JavaScript 确实执行并把数据集注入了页面，且**控制台零报错**。兵部还发现 [`README.md`](../README.md) 中有一处**占位符死链**：`[Poe Perplexity MCP Server](LINK)`，礼部按**方案 B —— 改为纯文本**处理，且**刻意不编造 URL**。

**终审（刑部）。** 刑部执行了 **13 项回归矩阵**，**全部 13 项通过**，并**签署交付，零回退**。

**第二轮：中英脱节，以及线上实测。** 门下认定**中文 README 已与英文版脱节**，并下达 **3 条硬约束**：① 英文 [`README.md`](../README.md) 是**唯一事实来源**，中文版须逐段与之对齐；② **不得编造**，凡属整理稿而非原始日志的文档**必须在文首标注**；③ 关于上线状态的表述**必须实测之后再据实书写**，并严格区分**实测事实与推断**。随后兵部**对线上站点做了实测**：截至 **2026-09-16 04:42 UTC** 的复核，站点根与 `/index.html`、`/styles.css`、`/app.js`、`/data/findings.json` 全部返回 **HTTP 200**；四项资源的 **sha256 与本地 `demo/` 文件逐字节一致**；CDN **无传播延迟**（`x-cache: HIT`，`last-modified` 早于探测约 11 小时）。基于这一实测结果，礼部**重新对齐了中文文档并改写部署说明**，移除所有「尚未上线 / 待激活」表述。

## 4. 纠错时刻（Correction moments）

本小节之所以存在，正是因为这才是该工作流的价值所在。若换成单一对话的工作方式，下列每一件事都极可能不被察觉地一路交付出去。而在这里，每一件都被评审或门禁拦下了。

### 4.1 一次数字颠倒，被质量门禁拦下

户部回奏的是**「5 名个人 + 12 个机构」**。数据集本身没有问题，错的是**对它的汇总**。刑部阶段3 的门禁裁定正确口径为 **12 名个人 + 5 个机构**，并将错误归因于回奏环节而非数据本身。错误的数字因此从未进入交付文档。

### 4.2 一次前提为假的派发修复 —— 被拒绝，而非「照单执行」

**F-5** 的派发前提是磁盘文件名带有 emoji 前缀。**工部复测后确认并无该前缀。** 工部没有机械地执行被要求的编辑，而是**拒绝并上报**：照单改动会指向并不存在的文件，从而**制造出失效引用**。这就是「听话的执行器」与「真正的部门」之间的差别 —— 它拦下了一个本已被放行施工的回归风险。

### 4.3 一次中英脱节，被审议环节退回

中文 README 已悄然与英文版产生差异。**门下予以封驳**，并且不是去修补表面症状，而是下达 3 条硬约束：英文为准、不得编造、上线结论须先实测。直到兵部**实测线上站点**之后，礼部才改写中文文档与部署说明 —— 因此最终措辞建立在实测之上，而非猜测之上。

> **小结：** 一次汇总口径的错误被门禁纠正；一个错误前提在造成损害之前被证伪；一份正在脱节的文档被退回并要求据实重写。三者之中，流水线每一次都付出了时间，以**避免交付缺陷**。
